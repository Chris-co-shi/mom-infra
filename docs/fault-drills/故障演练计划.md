# 故障演练计划

## 1. 目标

通过受控故障验证系统能否发现问题、限制影响、恢复服务并保留证据。故障演练不是随机破坏，也不是只看 Kubernetes 是否自动重启 Pod。

## 2. 前置条件

- 场景和爆炸半径已评审。
- 备份或回滚点可用。
- 关键指标、日志和 Trace 可查询。
- 有明确停止条件。
- 有负责执行、观察和恢复的角色。
- test/prod-like 环境没有真实业务数据。
- 运行手册已准备。

## 3. 演练等级

| 等级 | 范围 | 示例 |
|---|---|---|
| L1 | 单 Pod/单进程 | 应用 Pod 删除、Collector 重启 |
| L2 | 单组件 | Redis 中断、Nacos 不可用 |
| L3 | 单节点 | Worker 节点下线、存储压力 |
| L4 | 多组件链路 | MQ 中断 + 消费恢复 + 对账 |
| L5 | 灾难恢复 | 集群重建、数据库恢复 |

V1 优先完成 L1～L3，L4/L5 需要更充分的恢复准备。

## 4. 场景清单

### Kubernetes

- 应用 Pod 被删除。
- Worker 节点失联。
- Pod 因资源限制 OOM。
- 调度失败和 PVC Pending。
- Ingress 配置错误。

### PostgreSQL

- 数据库 Pod 停止。
- 连接数耗尽。
- 存储空间接近上限。
- 错误升级后回滚。
- 从备份恢复到新实例。

### Redis

- Redis 不可用。
- 内存达到阈值。
- 错误驱逐策略。
- 持久化文件损坏模拟。
- 恢复后限流和缓存状态变化。

### Nacos

- 注册中心短时不可用。
- 配置读取失败。
- 错误配置发布和回滚。
- 客户端重连风暴。

### RocketMQ

- Broker 中断。
- 消息重复投递。
- 消费者积压。
- 消费成功但 ACK 失败。
- 死信和人工补偿。

### Seata

- 服务端中断。
- 短事务回滚失败。
- 悬挂或超时事务处理。

### 可观测性

- Collector 不可用。
- Loki/Tempo/Prometheus 存储压力。
- Grafana 不可用。
- 遥测数据大量丢弃。

### 应用与设备链路

- Gateway 限流异常。
- PCS 命令超时或重复回执。
- WCS 运输任务超时、堵塞和人工接管。
- ERP 重复请求与重试风暴。

## 6. 停止条件

出现以下情况必须中止：

- 影响超出目标 Namespace 或组件。
- 管理通道存在失联风险。
- 备份或回滚点不可用。
- 数据出现无法解释的不一致。
- 恢复时间超过预定窗口。
- 关键观测能力同时失效。
- 有人员判断继续演练会扩大不可逆风险。

## 7. 观测要求

每个场景预先定义：

- 应触发的告警。
- 关键指标变化。
- 预期日志。
- Trace 中断或错误位置。
- Kubernetes Event。
- 业务侧失败与重试表现。

演练结束后对比“预期信号”和“实际信号”，没有信号的故障是需要修复的观测缺口。

## 8. 恢复验收

- 技术组件恢复健康。
- 关键业务链路恢复。
- 数据无不可解释丢失或重复。
- Outbox/Inbox、库存和消息完成对账。
- 告警恢复正常。
- 临时权限、网络放行和调试配置已清理。

## 9. Phase 01/02 建议顺序

```text
应用 Pod 删除
→ Collector 重启
→ Redis 短时不可用
→ Nacos 短时不可用
→ RocketMQ 重复投递
→ Worker 节点下线
→ PostgreSQL 恢复演练
```

每个场景通过后再提高复杂度，不同时注入多个未经验证的故障。
