# ADR-008：第三方组件部署方式

- 状态：Accepted
- 日期：2026-07-18
- 关联文档：[Phase 01 基础设施计划](../plans/Phase-01-基础设施计划.md)

## 1. 背景

PostgreSQL、Redis、Nacos、RocketMQ、Seata 和可观测性组件的部署复杂度不同。若全部手写 Kubernetes Manifest，会复制上游运维知识；若全部依赖 Helm 或 Operator，又可能把环境差异和升级行为隐藏在个人命令中。

## 2. 候选方案

### 方案 A：全部使用原生 YAML

优点：资源完全可见。

缺点：维护成本高，容易遗漏升级、探针、权限和持久化细节。

### 方案 B：全部使用 Helm Chart

优点：部署快，上游通常提供大量参数。

缺点：Chart 质量和维护状态不一致；环境差异可能散落在命令行；复杂状态组件仍可能需要 Operator。

### 方案 C：按组件复杂度选择，统一由 Git 管理输入和渲染验证

优点：兼顾上游能力与可审查性。

缺点：需要维护部署方式选择矩阵和统一校验入口。

## 3. 决策

采用方案 C：

1. Namespace、ServiceAccount、RBAC、NetworkPolicy、基础 ConfigMap 等仓库自有资源使用原生 Manifest + Kustomize。
2. 第三方组件优先使用官方或社区成熟、持续维护的 Helm Chart 或 Operator。
3. 有状态组件是否使用 Operator，必须在组件 PoC 前单独记录决策，重点验证备份、恢复、升级和故障行为。
4. Helm Chart 版本、镜像版本、镜像来源和关键 values 必须进入 Git。
5. CI 必须渲染并校验最终 Kubernetes 资源；禁止只验证 values 文件。
6. 禁止依赖个人工作站中的隐式 `--set` 参数。必要参数必须进入受版本控制的 values 或环境 Overlay。
7. 渲染产物默认不提交 Git，由 CI 和部署流程生成；恢复证据、Diff 和失败日志按 Runbook 留存。
8. 上游 Chart 或 Operator 的本地修改必须记录来源、版本和补丁原因。

## 4. 选择规则

| 场景 | 默认方式 |
|---|---|
| 仓库自有基础资源 | 原生 Manifest + Kustomize |
| 简单无状态第三方组件 | 固定版本 Helm Chart 或原生 Manifest |
| 复杂有状态组件 | 优先评估 Operator，再评估成熟 Helm Chart |
| 上游无可靠 Chart/Operator | 最小原生 Manifest，并补齐升级与恢复 Runbook |
| prod-like | 固定 Chart 版本、镜像 Tag，关键镜像使用 Digest |

## 5. 实施约束

- 每个组件目录必须声明 `deploymentMode`、上游来源和版本状态。
- 部署方式变更属于架构变更，需要 ADR 或组件决策记录。
- 任何方式都必须具备健康检查、资源限制、持久化、观测、升级、回滚和恢复入口。
- 不因采用 Operator 或 Helm 而把备份恢复责任转移给上游工具。

## 6. 后果

正向：避免无差别手写 Manifest，也避免不可审查的命令式部署；可按组件风险逐项验证。

负向：仓库需要同时维护 Kustomize、Helm values 和可能的 Operator CR，CI 工具链更复杂。

## 7. 验证

- 组件进入 PoC 前已有部署方式和来源记录。
- CI 能渲染最终资源并通过 Kubernetes Schema 校验。
- 相同 Git 提交在 Linux 与 Windows 能得到等价渲染结果。
- 部署、升级和回滚命令不依赖未记录的本地参数。
