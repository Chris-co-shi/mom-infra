# ADR-006：备份必须通过恢复验证

- 状态：Accepted
- 日期：2026-07-18
- 关联文档：[备份恢复与容灾](../disaster-recovery/备份恢复与容灾.md)

## 1. 背景

仅生成备份文件不能证明数据可恢复。格式错误、权限缺失、加密密钥丢失、版本不兼容和恢复步骤缺失都可能让备份在真正故障时失效。

## 2. 候选方案

### 方案 A：只监控备份任务成功

优点：实现简单。

缺点：无法验证备份内容和恢复流程。

### 方案 B：定期抽样恢复并做技术校验

优点：能发现大部分备份和恢复问题。

缺点：仍可能忽略业务关联和一致性。

### 方案 C：定期恢复并做技术与业务验证

优点：能够验证真实恢复能力和实际 RPO/RTO。

缺点：需要独立环境、时间和测试数据。

## 3. 决策

采用方案 C。备份只有在指定环境成功恢复，并通过技术和业务校验后才被认定为有效。

## 4. 实施约束

- 每个 Stateful 组件必须定义备份范围、频率、保留、加密和存储目标。
- 恢复演练不得直接覆盖唯一可用环境。
- 恢复后验证数据、权限、配置和业务关联。
- 记录实际 RPO、RTO 和失败原因。
- 备份文件与恢复密钥分离管理。

## 5. 后果

正向：

- 能真实评估恢复能力。
- 运行手册和人员操作能力得到验证。
- 可提前发现备份不可用和版本不兼容。

负向：

- 增加存储、计算和演练成本。
- 需要维护可重复的验证数据集。

## 6. 验证

Phase 01 至少完成 PostgreSQL 或 Redis 一次完整恢复；后续每个关键 Stateful 组件都必须有周期性恢复证据。
