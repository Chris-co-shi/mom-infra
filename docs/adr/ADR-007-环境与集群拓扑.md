# ADR-007：环境与集群拓扑

- 状态：Accepted
- 日期：2026-07-18
- 关联文档：[环境模型与晋级规则](../environments/环境模型与晋级规则.md)

## 1. 背景

仓库已经定义 `local`、`dev`、`test`、`prod-like` 四套 Overlay，但此前没有明确这些环境是否长期共存于同一个 Kubernetes 集群。原 Overlay 使用 `namePrefix` 修改 Namespace 名称，这会使文档中的固定 Namespace、RBAC、NetworkPolicy、监控查询和运行手册产生两套命名。

## 2. 候选方案

### 方案 A：四套环境长期共用一个集群

通过 Namespace 前缀区分环境。

优点：节省节点资源。

缺点：故障域、权限、存储和演练相互影响；资源名称与架构文档不一致；`prod-like` 无法形成独立的生产模拟边界。

### 方案 B：每套环境使用独立集群或独立 kube-context

所有环境保持相同的 Namespace 名称，通过目标集群和 kube-context 区分。

优点：环境边界清晰，Manifest 可直接晋级，运行手册和监控查询保持一致。

缺点：需要维护多个集群或按阶段重建环境。

### 方案 C：共享集群但使用独立 Namespace 前缀

优点：可同时运行多个环境。

缺点：所有 Namespace、RBAC、NetworkPolicy、Secret、监控和备份规则都必须环境化，显著增加 Phase 01 复杂度。

## 3. 决策

采用方案 B：

1. `local`、`dev`、`test`、`prod-like` 是独立部署目标，不通过 `namePrefix` 修改资源名称。
2. Namespace 固定为 `mom-system`、`mom-data`、`mom-messaging`、`mom-observability`、`mom-apps`。
3. `local` 可运行在开发者本地单节点集群。
4. `dev` 使用共享集成集群或独立 kube-context。
5. `test` 在具备资源后使用独立测试集群；未具备前只要求渲染和策略校验。
6. `prod-like` 使用独立三节点 k3s 集群，不与 `dev`、`test` 工作负载长期混跑。
7. 如果当前只有一套物理集群，同一时间只允许承载一个受管理环境；切换环境必须按 Runbook 清理、部署和验证。

## 4. 实施约束

- Overlay 必须增加 `mom.io/environment` 标签，但不得改变固定 Namespace 名称。
- 部署命令必须显式指定 kube-context，禁止依赖当前默认上下文。
- Secret、PVC、备份位置和域名按环境独立。
- `prod-like` 故障演练不得影响 `dev` 或 `test`。
- 未来若需要同集群多环境共存，必须新增 ADR，不得直接恢复 `namePrefix`。

## 5. 后果

正向：Manifest 晋级差异更小，Namespace、Runbook、监控和权限模型保持稳定，`prod-like` 故障域明确。

负向：需要额外集群资源或环境切换流程，无法默认在一套小型集群中长期同时运行四套环境。

## 6. 验证

- 四套 Overlay 渲染后 Namespace 名称一致。
- 每套 Overlay 都包含唯一的 `mom.io/environment` 标签。
- 部署脚本要求显式传入 kube-context。
- `prod-like` 部署证据记录独立三节点集群信息。
