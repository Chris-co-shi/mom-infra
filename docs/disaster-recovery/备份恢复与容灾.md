# 备份恢复与容灾

## 1. 基本原则

- 备份不是目标，可验证恢复才是目标。
- RPO/RTO 必须基于实测，而不是只写期望值。
- 数据恢复后必须进行技术和业务验证。
- 备份介质、凭证和恢复密钥必须受保护。
- 恢复流程需要考虑应用、数据库、消息和缓存之间的一致性。

## 2. 术语

| 术语 | 含义 |
|---|---|
| RPO | 可接受的数据丢失时间范围 |
| RTO | 从故障发生到业务恢复的目标时间 |
| 恢复点 | 可以恢复到的备份或日志位置 |
| 恢复证据 | 命令、日志、校验结果、截图和实际耗时 |

## 3. 组件恢复优先级

推荐基础恢复顺序：

```text
集群控制与网络
→ 存储
→ PostgreSQL / Redis
→ Nacos / RocketMQ / Seata
→ 可观测性基础组件
→ Gateway / IAM / MDM / Integration
→ MES / WMS / QMS / Traceability
→ PCS / WCS / Simulator
```

实际故障中应根据依赖、数据一致性和业务影响调整。

## 4. PostgreSQL

需要定义：

- 全量备份方式。
- WAL/PITR 策略。
- 备份频率和保留周期。
- 备份加密和存储目标。
- Schema、角色和权限是否纳入备份。
- 恢复到新实例的流程。
- Flyway 版本与恢复点兼容性。
- 恢复后库存、工单、质量和谱系校验。

恢复验收不能只执行 `SELECT 1`，至少验证关键 Schema、记录数量和业务关联。

## 5. Redis

需明确 Redis 中数据类型：

- 可从数据库重建的缓存。
- Token、黑名单等安全状态。
- 限流状态。
- 幂等状态。
- 临时会话。

不同数据的恢复要求不同。业务正确性不得只依赖 Redis 中不可恢复的唯一事实。

需要记录：

- RDB/AOF 策略。
- 内存和驱逐策略。
- 恢复后缓存预热方式。
- Token 与幂等状态丢失的影响。

## 6. RocketMQ

需要明确：

- Broker 与 NameServer 恢复顺序。
- 消息存储和保留策略。
- 消费位点恢复。
- 重复投递和积压处理。
- 死信队列和人工补偿。
- 恢复后 Outbox/Inbox 对账。

消息恢复后出现重复投递属于可预期情况，应用必须依靠幂等处理。

## 7. Nacos 与 Seata

Nacos：

- 配置权威来源和导出方式。
- 注册中心短时不可用时客户端行为。
- 配置恢复后的版本核对。

Seata：

- 服务端配置与数据库恢复。
- 未完成全局事务的处理。
- 仅用于既定短事务边界，不把长生产流程恢复依赖于单个全局事务。

## 8. Kubernetes 集群

需要保留：

- k3s 安装参数和版本。
- 节点网络、Token 和证书恢复说明。
- Kubernetes 资源均可由 Git 重建。
- PVC 数据单独备份。
- 节点替换和重新加入流程。
- Ingress、DNS、TLS 验证。

Git 中可重建的 Manifest 不等于持久卷数据已经备份。

## 9. 恢复验证

技术验证：

- Pod、Service、Endpoint、PVC。
- 数据库连接和数据完整性。
- Redis 连接与关键状态。
- RocketMQ 生产、消费、积压和重复处理。
- Nacos 注册与配置读取。
- Trace、Log、Metric 恢复。

业务验证：

- 登录和权限。
- 送货、检验、入库等关键查询。
- 工单和库存状态。
- MQ 事件闭环。
- 批次正反向追溯。
- PCS/WCS 命令恢复。

## 10. 恢复演练记录

每次演练记录：

- 故障场景。
- 起始时间和发现方式。
- 选择的恢复点。
- 实际数据丢失范围。
- 实际 RTO。
- 执行步骤和人工决策。
- 技术与业务验证。
- 未解决风险。

## 11. Phase 01 最小要求

- PostgreSQL 或 Redis 至少完成一次备份恢复实测。
- Runbook 由第二人按文档重复执行。
- 记录实际耗时和数据校验。
- 备份文件不进入 Git。
- 恢复证据不包含敏感信息。
